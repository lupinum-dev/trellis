# 0005: Canonical MCP Bearer-Key Auth

Status: Proposed
Date: 2026-06-03

## Summary

Trellis should provide a complete bearer-key auth slice for workspace MCP apps. MCP itself remains
opt-in, but once a workspace app runs `trellis add mcp`, protected bearer-key auth should be generated by
default and tested as the canonical production path.

## Problem

Bearer-key MCP auth crosses schema, token generation, hashing, revocation, middleware validation, actor
mapping, workspace membership, trusted forwarding, UI/API token creation, and tests. Reimplementing that
in every app is both noisy and security-sensitive.

The risk is not only code volume. The risk is inconsistent security:

- raw tokens stored by mistake
- revoked keys accepted
- workspace membership not checked
- `lastUsedAt` writes on every request
- wrong caller forwarded into Convex
- MCP access granted without permission checks

## Before

An official app baseline implements its own `mcpKeys` schema, domain functions, middleware, token
creation route, one-time display behavior, revoke behavior, and trusted Convex caller mapping.

## After

`trellis add mcp` generates the blessed workspace MCP key slice. Apps can customize product UI and tool
behavior, but the core bearer-key security path starts from one maintained pattern.

Public unauthenticated MCP is not the generated production default. If an app needs it for a local demo or
advanced integration, that path must be explicit and visibly advanced.

## Proposal

The generated slice should include:

- `mcpKeys` table with hash-only token storage
- indexes for hash lookup and workspace/admin views
- secure token generation with one-time raw token display
- revoke mutation
- touch/last-used behavior with debounce or minimum interval
- middleware that validates `Authorization: Bearer <token>`
- invalid bearer throttling
- workspace membership and permission validation
- mapping to an MCP caller and optional acting-for user
- tests for active, revoked, missing, malformed, wrong-workspace, and repeated-invalid-token cases

Keep this as an opt-in generated slice. Do not add the table to non-MCP apps and do not create a hidden
database requirement when MCP is disabled.

For packaged integrations, this RFC applies to official Trellis workspace app starters and `trellis add
mcp`. Integrations such as a CMS may use domain-specific token tables and tools if they satisfy the same
invariants: hash-only storage, one-time raw token return, revocation, workspace or tenant binding,
permission checks, bounded `lastUsedAt` writes, trusted forwarding, malformed bearer throttling, and
tests.

## Tradeoffs

This creates app-owned generated domain code instead of hiding everything inside the package. That is the
right boundary because the table lives in the app Convex schema and the app may need to display, revoke,
or audit keys. Trellis should own the pattern, not make a black box.

The cost is an extra table when MCP is enabled. That cost is justified because bearer-key auth is a real
MCP requirement, not speculative flexibility.

## Rejected Options

- Package-level table abstraction: rejected because Convex schema is app-owned and should stay visible.
- Require every app to implement bearer auth manually: rejected because it repeats security-sensitive
  code.
- Store raw tokens for convenience: rejected categorically.
- Make bearer auth default for all workspace apps: rejected because MCP is optional and tables are
  expensive.
- Generate public unauthenticated MCP by default: rejected because it is too easy to expose accidentally.

## Acceptance Criteria

- MCP bearer keys are hash-only after creation.
- Raw token is returned once and cannot be recovered.
- Revoked keys are rejected.
- Keys are scoped to a user and workspace.
- Middleware maps valid keys to a clear MCP caller shape.
- Permission checks can prevent MCP access even when a key is valid.
- Last-used updates are rate-limited or otherwise bounded.
- The generated slice has invariant tests.
- `trellis add mcp` generates bearer-key MCP auth by default for workspace apps.
- Public or anonymous MCP requires an explicit advanced/local-only path and is not the starter default.
- Packaged integrations can use domain-specific token tables only when they meet the same security
  invariants and tests.

## Verification

- Convex tests for key creation, hash lookup, revoke, workspace mismatch, and permission denial.
- Server tests for middleware validation and invalid bearer throttling.
- Tests that raw tokens are returned once and never stored.
- Tests that malformed bearer attempts are throttled.
- Tests that `lastUsedAt` writes are bounded.
- CLI add-slice typecheck.
- Doctor finding for expected identity-forwarding key when MCP bearer auth is present.
