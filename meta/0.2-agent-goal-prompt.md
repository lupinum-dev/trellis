## Product Standard

Trellis should feel like Vue/Nuxt for Nuxt + Convex + Better Auth + MCP apps:

- one obvious beginner path
- generated apps work before the user edits anything
- conventions install boring lifecycle automatically
- diagnostics fail near the cause
- advanced APIs remain available, but are not equal beginner choices

The desired balance is: easy to set up, difficult to misuse, mostly rigid by default, flexible through
explicit advanced escape hatches.

## Engineering Bias

Default preference:

delete > simplify > replace > add

Before adding code, tables, wrappers, adapters, projections, config, generated files, MCP helpers,
bridge exports, compatibility paths, or public API, ask:

- Can we delete something instead?
- Can the existing path be simplified?
- Can this be one direct command or function?
- Is this a real 0.2 requirement, or imagined future flexibility?
- What acceptance criterion proves this needs to exist?

Prefer hard cutovers for unreleased and greenfield paths. Do not keep old and new beginner APIs side
by side.

## Hard Constraints

- Do not add compatibility shims, feature flags, duplicate generated descriptors, generic adapters, or
  second sources of truth unless an explicit acceptance criterion requires them.
- Do not add permission override tables, grants, denies, role overlays, record sharing, audit tables,
  scoped DB wrappers, generic integration adapters, or public unauthenticated MCP defaults in 0.2.
- Do not add `ctx.scope.table(...)`, `ctx.scope.insert(...)`, or any scoped DB abstraction in 0.2.
- `workspaceScope()` stops at validated `ctx.workspaceId`.
- Keep explicit `workspaceId` filters and writes visible in generated workspace code.
- Keep domain policy out of bridge and transport layers.
- Keep Ginko CMS and the shadcn Trellis template as consumers, not dependencies inside Trellis core.
- Keep `@lupinum/trellis` as the Nuxt module entry.
- Keep `@lupinum/trellis/app` as the beginner app API.
- Do not publish packages unless the human explicitly asks you to publish.

## Final 0.2 Experience

New app:

```bash
pnpm dlx @lupinum/trellis init my-app
cd my-app
pnpm install
pnpm dev
```

Additive ladder:

```bash
trellis add auth
trellis add workspace
trellis add mcp
```

Beginner app authoring surface:

```ts
import { operation, workspaceScope } from '@lupinum/trellis/app'
```

Nuxt module entry:

```ts
export default defineNuxtConfig({
  modules: ['@lupinum/trellis'],
})
```

Primary objective:

Make `operation` the canonical beginner authoring primitive. A beginner should not need to choose
between descriptors, manifests, backend builders, MCP wrappers, tenant isolation internals, and bridge
mechanics before defining and calling one useful operation.

## Acceptance Gate

0.2 is not ready for human release until all of these are true:

- A user can start with `trellis init my-app`.
- The same app can progressively add auth, workspace, and MCP.
- One operation definition drives Convex, permission understanding, destructive safety, and MCP
  projection.
- Workspace apps use validated `ctx.workspaceId` without scoped DB wrappers.
- Auth bootstrap and MCP runtime setup are Trellis-owned by default.
- Permissions are explainable before extra authorization tables exist.
- Starters, examples, docs, and templates all teach the same path.
- Ginko-style integrations can compose Trellis invariants without exposing Trellis as their public
  setup product.
- Hard-cut release notes exist and name the advanced escape hatches.
- `pnpm run release:verify` passes.
