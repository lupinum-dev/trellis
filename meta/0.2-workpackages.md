# Trellis 0.2 Workpackages

Status: Active planning
Date: 2026-06-03

This checklist is the implementation tracker for Trellis `0.2 Operation Ladder`.

Source of truth:

- [Roadmap](../ROADMAP.md)
- [RFC 0011: Hard-Cut Operation Ladder Release](./rfc/0011-hard-cut-operation-ladder-release.md)

Use this file to hand work to implementation agents. RFCs explain why the release should work this way;
this file tracks what must be built and how to prove each phase is done.

## Operating Rules

- [ ] Prefer hard cutovers over compatibility paths.
- [ ] Keep `@lupinum/trellis` as the Nuxt module entry.
- [ ] Add `@lupinum/trellis/app` as the beginner app API.
- [ ] Keep advanced APIs available but out of the beginner path.
- [ ] Do not add permission override tables, role overlays, record sharing, audit tables, scoped DB
  wrappers, generic adapters, or public unauthenticated MCP defaults in `0.2`.
- [ ] Every generated app must work before the user edits it.
- [ ] Every added capability must have one canonical generated path and one doctor/conformance story.

## Phase 2: Operation Core

Goal: make operation definitions the canonical authoring primitive.

- [ ] Implement operation metadata: id, args, auth, permission, safety, and handler shape.
- [ ] Implement operation projection to Convex handlers.
- [ ] Implement operation projection to browser/server callers where existing internals support it.
- [ ] Ensure schema, permission, and operation id are declared once.
- [ ] Delete duplicated generated descriptors when the operation definition can be the source.

Acceptance criteria:

- [ ] One operation definition can produce the Convex handler surface needed by generated apps.
- [ ] Operation args are declared once and reused by projections.
- [ ] Operation permission metadata is declared once and reused by runtime checks and explain output.
- [ ] Existing lower-level internals can still be used through advanced paths, not beginner docs.

Verification:

- [ ] Add runtime tests proving operation projections register Convex handlers correctly.
- [ ] Add tests proving operation id and args survive projection.
- [ ] Run focused package tests and typecheck.

## Phase 3: Workspace Scope

Goal: remove repeated workspace-id boilerplate without creating a second database abstraction.

- [ ] Implement `workspaceScope(...)` as explicit operation metadata.
- [ ] Validate that workspace operations receive `ctx.workspaceId`.
- [ ] Make `ctx.workspaceId` the only new scope value in `0.2`.
- [ ] Do not add `ctx.scope.table(...)`, `ctx.scope.insert(...)`, or scoped DB wrappers.
- [ ] Make generated workspace operations use explicit `ctx.workspaceId` in queries and writes.

Acceptance criteria:

- [ ] Workspace operations fail near the cause when `ctx.workspaceId` is missing.
- [ ] Generated workspace code does not manually repeat identity extraction boilerplate.
- [ ] Generated workspace code still shows explicit `workspaceId` filters and writes.
- [ ] No second tenant source of truth is introduced.

Verification:

- [ ] Add tests for valid workspace operations.
- [ ] Add tests for missing workspace context.
- [ ] Add tests proving generated examples use explicit `ctx.workspaceId`.

## Done Definition

Trellis `0.2` is done when:

- [ ] A user can start with `trellis init my-app`.
- [ ] The same app can progressively add auth, workspace, and MCP.
- [ ] One operation definition drives Convex, permission understanding, destructive safety, and MCP
  projection.
- [ ] Workspace apps use validated `ctx.workspaceId` without scoped DB wrappers.
- [ ] Auth bootstrap and MCP runtime setup are Trellis-owned by default.
- [ ] Permissions are explainable before extra authorization tables exist.
- [ ] Starters, examples, docs, and templates all teach the same path.
- [ ] Ginko-style integrations can compose Trellis invariants without exposing Trellis as their public
  setup product.
- [ ] `pnpm run release:verify` passes.
