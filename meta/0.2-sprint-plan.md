## Sprint Principle

Do not reopen feature scope unless review finds a release-blocking defect.

The target is a hard-cut `0.2` release that is easy to start, difficult to misuse, mostly rigid by
default, and flexible only through explicit advanced escape hatches.

## Review Focus

Review should look for release blockers, not polish work.

- Does any changed file create a second source of truth?
- Does any beginner doc still teach old backend builders, descriptors, manifests, MCP wrappers, or
  bridge mechanics as an equal first path?
- Did any compatibility shim, dual path, generic adapter, scoped DB wrapper, authz table, role overlay,
  record sharing model, audit table, or public unauthenticated MCP default slip in?
- Do starters and examples still show explicit `ctx.workspaceId` filters and writes after
  `workspaceScope()` validation?
- Does `trellis add auth`, `trellis add workspace`, and `trellis add mcp` fail near the cause when host
  files would be overwritten or when required runtime setup is missing?
- Are Ginko CMS and the shadcn template consuming Trellis invariants without becoming Trellis core
  dependencies or forcing product-specific setup into Trellis?

## Suggested Sprint Execution

Use this order for the final release sprint:

1. Freeze scope.
   Confirm that no new `0.2` feature work is being accepted unless a review finds a release blocker.

2. Review Trellis diff.
   Run `git status --short`, `git diff --stat`, and targeted `git diff` passes over public API, CLI,
   generated starters, examples, docs, tests, and package metadata.

3. Review consumers.
   Confirm Ginko remains clean against the local tarballs. Review the shadcn template's pending diff
   and its `human-todo.md` before treating it as official.

4. Rebuild tarballs if Trellis changes.
   If any Trellis source, package metadata, or bridge package content changes, rebuild local tarballs
   before consumer checks.

5. Run final gates.
   Run Trellis `pnpm run release:verify`. Then run Ginko CMS `pnpm run check` and shadcn template
   `pnpm run check` if tarballs or consumer-relevant surfaces changed.

6. Prepare handoff.
   Write the commit/PR summary with verification evidence, non-goals, consumer status, and the explicit
   note that publishing remains human-controlled.

## Sprint Exit Criteria

The sprint exits only when:

- [ ] Trellis diff review is complete.

- [ ] Trellis final release gate passes after the last code/package/tarball change.
- [ ] Consumer checks pass after the final Trellis tarball, or any skipped consumer check is explained.
- [ ] The release handoff names every remaining human decision.
- [ ] No publish has happened without explicit approval.
