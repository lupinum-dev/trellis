Every term Trellis uses in more than one guide is defined here. Pages link to these anchors instead of redefining terms inline.

The terms cluster into four groups: **identity**, **authorization**, **structure**, and **transports**.

::note
This page is reference, not onboarding. A basic app does not need every term here on day 1. Start with [Start here](/docs/getting-started/start-here) and come back only when a guide sends you here.
::

## Identity

### Caller

How a call arrived. Typical callers are an anonymous browser visitor, a signed-in user session, a forwarded agent request, or a trusted server caller. A caller comes from transport signals like cookies, tokens, and signatures. It does not know roles, tenants, or product policy.

### AppIdentity

Who the caller is in your app. Carries things like `role`, `workspaceId`, and workspace membership. A browser session and an MCP agent request can resolve to the same appIdentity. That is the point: product permission stays the same even when the caller changes.

### Permission appIdentity

A relaxed appIdentity shape used only by frontend access context. It can return a value for anonymous users so the UI can compute `can(...)` results without branching. Backend handlers still use the stricter appIdentity.

## Authorization

### Guard

A reusable authorization check defined with `defineGuard(label, check)`. Guards answer broad entry questions for protected handlers and migration code. Normal app code should prefer explicit `authenticated` or `workspace` lanes plus operation `permission`, `load`, and `authorize`.

### Check

An appIdentity-aware boolean predicate. Permissions and custom guards are named checks. Resource-bound predicates like `canUpdateTodo(todo)` are another form. Evaluate a check against the current appIdentity with `can(...)`.

### Load

The handler phase that fetches the data a downstream decision depends on. Runs
after lane admission and static permission checks, before `authorize`. Common
pattern: load the record, confirm it exists with `requireRecord`, return it in
the context object.

### Authorize

The resource-bound authorization phase that runs against loaded data. Use it when the decision to allow an action depends on the thing being acted on — ownership, state, relationships. Keeps resource-specific policy out of the coarse entry guard.

### Operation

A reusable product action. An operation bundles `permission`, `load`, `authorize`, `preview`, and `handler` into one unit so a mutation, MCP tool, and confirmation UI can all use the same checks.

### Preview

The read-only projection of what an operation _would_ do, used to power confirmation UX for destructive work. Returns one envelope with `allowed`, `summary`, `blockers`, `warnings`, `effects`, `confirm`, and optional app-owned `details`. When destructive confirmation is configured, Trellis also adds confirmation material that execution checks before applying the mutation.

### Destructive

An operation `kind` that requires extra safety: a preview phase must exist, and the confirmation token must match before execution. Reserved for actions that lose or mutate data in ways you can't cheaply undo.

## Structure

### Business layer

The Convex backend path every caller should go through. One schema, one set of checks, one authorization path. Trellis exists to keep browser, server, webhook, and agent code from forking those rules.

### Handler

The execution function of a query, mutation, action, or operation. Runs last in the phase chain (`guard -> load -> authorize -> handler`) and does the actual work.

### Tenant

The isolation scope for multi-tenant data — typically a workspace, organization, or team. In Trellis, tenant boundaries are enforced at runtime, not just by convention.

### Isolation

Runtime enforcement, configured in `defineTrellis(...)`, that rewrites `ctx.db` queries to filter by the current appIdentity's tenant. Tables listed under `isolation.tables` get automatic scoping; the default field is `workspaceId`.

### Unsafe path

The explicit exception family for review-sensitive paths. Trellis exposes named `crossTenant` capabilities for reviewed cross-scope data access and `query.unsafe(...)` / `mutation.unsafe(...)` for intentional handler-level bypasses. Using either one is an explicit decision, not the default.

## Transports

### Transport

How a call reaches the backend: browser UI, Nitro server route, webhook, or MCP agent. Transports differ in identity, result shape, and outer protections. They should not differ in product authorization.

### Projection

A caller-facing wrapper, such as a Nuxt composable, server helper, or MCP tool. It exposes the same backend action in the shape that caller needs. The logic stays in Convex.

### App Runtime

The protected Convex backend path: caller resolution, appIdentity resolution, tenant scoping, protected queries and mutations, actions, and operations.

### Nuxt Runtime

The Nuxt-facing path: SSR, hydration, composables (`useConvexQuery`, `useConvexMutation`), route protection, server helpers, upload helpers, and access context.

### Agent Runtime

The MCP-facing path: tool exposure, permission-aware tool discovery, destructive preview and confirmation, and caller forwarding into the App Runtime.
