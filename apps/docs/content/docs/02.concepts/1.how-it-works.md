Trellis tries to prevent one specific mess: browser code, server routes, webhooks, and agents all growing their own copies of the same rules.

The fix is simple to say and easy to drift away from:

Put the rules in Convex. Let every caller go through that path.

This page explains the model. If you only need definitions, use the [Glossary](/docs/concepts/glossary).

## The core sequence

Every protected call follows the same shape:

1. A [caller](/docs/concepts/glossary#caller) tells Trellis how the call arrived.
2. Your app resolves an [appIdentity](/docs/concepts/glossary#appIdentity) from that caller.
3. Tenant rules decide which data the appIdentity can even see.
4. [Guards](/docs/concepts/glossary#guard) and [authorization](/docs/concepts/glossary#authorize) decide whether the work is allowed.
5. [Operations](/docs/concepts/glossary#operation) package flows that need preview, confirmation, or reuse.

That is the shape. The caller may be a browser session, a Nitro route, a webhook, or an MCP tool. The backend rule path stays the same.

## One backend path, many callers

Without Trellis, teams often build one path for the browser, another for webhooks, another for server routes, and another for agents. At first they match. Later, one path forgets a role check or skips a tenant filter.

That is the bug Trellis is built to make harder.

Each caller has different transport details. A browser has cookies. An MCP tool may have a bearer key. A webhook may have a signature.

Those details decide how the call enters the system. They do not replace the backend authorization check.

## Caller first, appIdentity second

This split matters.

A [caller](/docs/concepts/glossary#caller) answers:

> How did this call arrive?

An [appIdentity](/docs/concepts/glossary#appIdentity) answers:

> Who is this caller in my app?

The caller is transport-shaped: anonymous visitor, signed-in session, forwarded agent, trusted server call.

The appIdentity is product-shaped: user id, role, workspace membership, tenant scope.

Do not collapse them. "This request came from a webhook" does not mean it can do anything. "This user is signed in" does not mean they are an admin. The appIdentity is where your product rules begin.

Two callers can resolve to the same appIdentity. For example, a signed-in browser session and an MCP agent acting for that user can both become the same workspace member. That is the point: transport changes, product permission does not.

## What changes by caller

Different callers still need different outer checks:

- Browser pages need session handling and hydration.
- Server routes need forwarded identity or trusted server credentials.
- Webhooks need signature checks.
- MCP tools need bearer auth, tool visibility, and sometimes confirmation.

Trellis does not flatten those differences. It keeps them at the edge, then routes the real work through the backend rule path.

::warning
Transport checks are not authorization. A hidden MCP tool, a private server route, or a verified webhook signature only proves how the call reached you. The handler still needs the right guard, load, authorize, and handler logic.
::

Signed identity forwarding follows the same rule. A valid `_trellisForwarding` envelope proves the call crossed an approved boundary. It does not grant permission, skip appIdentity resolution, or replace backend checks.

## Why operations exist

[Operations](/docs/concepts/glossary#operation) are for actions that need to be reused or confirmed.

Use an operation when the same action needs to appear in more than one place:

- a UI button
- a confirmation preview
- a server workflow
- a webhook
- an MCP tool

Write the permission, load, authorize, preview, and handler once. Then project that operation into each caller path.

Not every mutation needs an operation. Use one when preview, confirmation, destructive safety, or reuse is real. Otherwise keep the mutation direct.

## What Trellis does not own

Trellis does not decide your product rules.

You own:

- what a user is
- what a workspace is
- what tables exist
- which roles can do what
- what counts as destructive
- what each handler actually changes

Trellis owns the framework path around those rules so they do not fork across callers.

## When the model matters

For a small public app, most of this page is background.

The model starts paying for itself when you add:

- auth
- workspace data
- roles
- protected mutations
- server routes
- webhooks
- MCP tools

That is when copied authorization rules become expensive.

## Common pitfalls

- Treating a transport as a product role.
- Forking server or agent code into special business handlers.
- Relying on tool visibility or webhook signatures as if they were authorization.
- Reading this page again when the next useful step is building the task guide.
