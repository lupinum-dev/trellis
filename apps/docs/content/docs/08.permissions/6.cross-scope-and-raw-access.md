Trellis gives you one default path and two explicit exception surfaces. They
are not interchangeable. Use the narrowest surface that does the job and make
the reason visible in review.

| Surface | Bypasses | Still enforces | Requires | Emits |
| --- | --- | --- | --- | --- |
| `ctx.db` | Nothing | Isolation, services, triggers | Normal handler lane | Runtime denial events |
| `crossTenant` capability | Tenant isolation for declared tables | Table allow-list, read/write mode, services, triggers | `reason`, `tables`, narrow methods | `db.cross_tenant.used` |
| `query.unsafe(...)` / `mutation.unsafe(...)` | Protected handler path | Convex runtime + surrounding infra | Typed `permit` | `unsafe.handler.used` |

Preference order: `ctx.db`, then a named `crossTenant` capability, then unsafe
lanes. Do not use an unsafe lane just to avoid modeling a reviewed
cross-tenant read.

## Default: `ctx.db`

For tenant-isolated tables, `ctx.db` enforces the active tenant boundary on
reads and writes. Use it unless the handler is explicitly meant to cross
workspaces or tenants.

## Named Cross-Tenant Capabilities

Declare cross-tenant work at the handler export. The capability gets the
cross-tenant DB internally, but the handler receives only the narrow methods
you expose.

```ts [convex/agency/posts.ts]
export const listAgencyPosts = query.protected({
  args: {},
  guard: agencyAdmin,
  crossTenant: {
    reason: 'Agency portfolio views span assigned client workspaces.',
    tables: ['posts'],
    access: ({ db }) => ({
      listPosts: async () => await db.query('posts').collect(),
    }),
  },
  handler: async (ctx) => {
    return await ctx.crossTenant.listPosts()
  },
})
```

Cross-tenant reads are the default. Write capabilities must be
operation-backed and declare `mode: 'write'`.

```ts [convex/workspaces/domain.ts]
export const createWorkspaceOp = operation.mutation({
  id: 'workspaces.create',
  args: createWorkspace.args,
  crossTenant: {
    mode: 'write',
    reason: 'Workspace bootstrap runs before the caller has a tenant scope.',
    tables: ['workspaces', 'memberships'],
    access: ({ db }) => ({
      createWorkspace: async (input) => {
        const workspaceId = await db.insert('workspaces', input.workspace)
        await db.insert('memberships', input.membership)
        return workspaceId
      },
    }),
  },
  handler: async (ctx, args) => {
    return await ctx.crossTenant.createWorkspace(args)
  },
})
```

What still applies:

- The handler must use an explicit lane.
- The capability can touch only declared tables.
- Read capabilities cannot write.
- Write capabilities require an operation id.
- Observability records every table touch as `db.cross_tenant.used`.

## Unsafe Lanes

`query.unsafe(...)` / `mutation.unsafe(...)` are for cases where the handler
itself must be declared outside the normal protected builder path.

```ts [convex/features/uploads/domain.ts]
import { unsafe } from '@lupinum/trellis/backend'

export const generateUploadUrl = mutation.unsafe({
  permit: unsafe.permit({
    kind: 'preTenantUpload',
    reason: 'Generate upload URLs before a concrete tenant-scoped record exists.',
    scope: ['assets'],
  }),
  args: {},
  handler: async (ctx) => {
    requireAuth(await ctx.appIdentity())
    return await ctx.storage.generateUploadUrl()
  },
})
```

::caution
Unsafe lanes are not a substitute for a cross-tenant capability. If the normal
handler shape still works and only data access crosses tenants, declare a
capability at the export.
::

## Real-App Cases

From the maintained examples:

- Current-workspace work: normal tenant-scoped handlers.
- Share-token reads: named read capability for `shareTokens` and `articles`.
- Workspace bootstrap: operation-backed write capability for `workspaces` and
  `memberships`.
- Public runbook catalog: named read capability bounded to public records.
- Upload URL generation before a concrete record exists: `mutation.unsafe(...)`.

Each exception is visible at the export. No quiet helper silently crosses
tenant boundaries.

## Common Pitfalls

- Treating cross-tenant access as normal app data access.
- Returning a generic DB object from a capability instead of narrow methods.
- Adding write mode to a non-operation handler.
- Hiding a capability inside a helper where reviewers cannot see why the
  boundary changed.
- Using an unsafe lane to avoid modeling the right appIdentity or tenant flow.
