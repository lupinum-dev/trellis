Most Trellis code should use the normal lane for its product boundary:

- `query.public` only for genuinely public reads
- `query.authenticated` / `mutation.authenticated` for signed-in personal work
- `query.workspace` / `mutation.workspace` for tenant-scoped work
- operations for reusable business actions, especially destructive work

Everything on this page is an exception path. Use the narrowest one that
does the job and make the reason visible in review.

## Review Table

| Path                               | What it bypasses                                                      | What still applies                                                         | Safer default                             | Required proof                                      |
| ---------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------- |
| `query.public`                     | signed-in caller and appIdentity                                      | public table allow-list, normal handler code                               | `authenticated` or `workspace`            | test that data is safe for anonymous callers        |
| `mutation.public` + `publicWrite`  | signed-in caller and appIdentity for an operation-backed public write | declared tables, narrow `publicWrite` methods, operation id, observability | authenticated/workspace mutation          | explicit reason, operation-backed write test        |
| `crossTenant`                      | active tenant isolation for declared tables                           | table allow-list, read/write mode, services, triggers, observability       | normal `ctx.db`                           | allowed/disallowed tenant tests                     |
| `query.unsafe` / `mutation.unsafe` | normal lane guard phases                                              | Convex runtime and surrounding infrastructure                              | protected/workspace lane or `crossTenant` | typed permit, reason, scope, reviewer notes         |
| `actingFor`                        | direct browser-user caller shape                                      | signed forwarding, backend appIdentity resolution, tenant checks           | normal caller identity                    | delegation test and scope/expiry proof              |
| service callers                    | user session identity                                                 | restricted tables, tenant derivation, replay policy, audit metadata        | user/workspace lane                       | service-subject metadata and tests                  |
| forwarded callers                  | local transport identity                                              | signed envelope, purpose, args hash, TTL, backend authorization            | direct server auth or normal session      | forged/expired/mismatched envelope tests            |
| server `auth: 'none'`              | server helper auth attachment                                         | target handler's own lane, or route-owned transport proof                  | `auth: 'required'` or signed forwarding   | doctor inventory, explicit reason, route proof test |
| public table reads                 | private table default                                                 | configured public read table list                                          | authenticated/workspace read              | anonymous read test and table review                |

## Preference Order

Use this order when deciding whether an exception is justified:

1. normal lane with `ctx.db`
2. operation-backed public write or named `crossTenant` capability
3. service/forwarding lane with signed transport proof
4. unsafe lane with typed permit

If the normal handler shape still works and only data access crosses tenants,
declare a narrow capability instead of using an unsafe lane.

## Public Reads And Writes

Public reads are for data that is intentionally anonymous. Tables are private by
default; add public read tables only when anonymous callers may see every row
returned by that handler.

Public writes must be operation-backed and narrow:

```ts [convex/features/todos/domain.ts]
export const createTodoOp = operation.publicMutation({
  id: 'todos.create',
  args: createTodo.args,
  publicWrite: {
    reason: 'Public todo demo allows anonymous todo creation.',
    tables: ['todos'],
    access: ({ db, args }) => ({
      createTodo: async () => await db.insert('todos', args),
    }),
  },
  handler: async (ctx) => {
    return await ctx.publicWrite.createTodo()
  },
})
```

Do not use public lanes because auth setup is inconvenient. If the answer
depends on who is calling, the handler is not public.

## Named Cross-Tenant Capabilities

Declare cross-tenant work at the handler or operation export. The capability
gets the cross-tenant DB internally, but the handler receives only the narrow
methods you expose.

```ts [convex/agency/posts.ts]
export const listAgencyPosts = query.protected({
  args: {},
  guard: agencyAdmin,
  crossTenant: {
    reason: 'Agency portfolio views span assigned client workspaces.',
    tables: ['posts'],
    access: ({ db }) => ({
      listPosts: async () => await db.query('posts').collect(),
    }),
  },
  handler: async (ctx) => {
    return await ctx.crossTenant.listPosts()
  },
})
```

Cross-tenant reads are the default. Write capabilities must be
operation-backed and declare `mode: 'write'`.

## Unsafe Lanes

`query.unsafe(...)` / `mutation.unsafe(...)` are for cases where the handler
itself must be declared outside the normal protected builder path.

```ts [convex/features/uploads/domain.ts]
import { unsafe } from '@lupinum/trellis/backend'

export const generateUploadUrl = mutation.unsafe({
  permit: unsafe.permit({
    kind: 'preTenantUpload',
    reason: 'Generate upload URLs before a concrete tenant-scoped record exists.',
    scope: ['assets'],
  }),
  args: {},
  handler: async (ctx) => {
    requireAuth(await ctx.appIdentity())
    return await ctx.storage.generateUploadUrl()
  },
})
```

Unsafe lanes are not a substitute for a cross-tenant capability, a missing guard,
or a missing appIdentity model.

## Server `auth: 'none'`

`auth: 'none'` is valid when calling a genuinely public handler, or when a route
owns a complete transport security model and the backend target still validates
the business rules it owns.

It is invalid as a shortcut around missing session auth, missing forwarding, or
missing service binding.

Prefer:

- `auth: 'required'` for session-backed server routes
- signed forwarding when a trusted route must act across a server boundary
- a public handler only when the data/action is genuinely public

## Anti-Patterns

### Trusting Tenant Args

Bad:

```ts
export const update = mutation.workspace({
  args: { workspaceId: v.id('workspaces'), id: v.id('todos') },
  handler: async (ctx, args) => {
    await ctx.db.patch(args.id, { workspaceId: args.workspaceId })
  },
})
```

Good:

```ts
export const update = mutation.workspace({
  args: { id: v.id('todos'), title: v.string() },
  load: async (ctx, args) => await ctx.db.get(args.id),
  authorize: (todo, { appIdentity }) => todo?.workspaceId === appIdentity.workspaceId,
  handler: async (ctx, args) => {
    await ctx.db.patch(args.id, { title: args.title })
  },
})
```

### Frontend-Only Authorization

Bad: hiding a button and trusting that no forbidden call will happen.

Good: use `_can` for UX, then keep the backend `authorize` check as the source
of truth.

### Route-Owned Business Permission

Bad: webhook HMAC passes, then the Nitro route directly writes tenant data as if
the route were the business authority.

Good: the route verifies transport reach, forwards or calls a backend service
path, and Convex revalidates service/user/workspace binding before the write.

### Raw Agent Writes

Bad: an MCP destructive tool directly calls a mutation.

Good: the MCP tool binds to an operation preview/confirm/execute flow, and the
operation runs the same backend permission checks as browser/server callers.

## Doctor And Manual Review

`trellis doctor --production` should be part of every review that uses these
paths. Doctor can inventory unsafe handlers, cross-scope capabilities,
forwarded-caller misuse, MCP destructive-tool misuse, weak forwarding keys, and
MCP rate-limit store risk.

Doctor cannot prove every app-specific business reason. When a row needs manual
review, keep the reason in the code near the export and add a test that proves
the narrow allowed case and the denied case.

## Real-App Cases

From the maintained examples:

- Current-workspace work: normal tenant-scoped handlers.
- Share-token reads: named read capability for `shareTokens` and `articles`.
- Workspace bootstrap: operation-backed write capability for `workspaces` and
  `memberships`.
- Public runbook catalog: named read capability bounded to public records.
- MCP writes: operation-backed tools over the workspace backend model.
- Upload URL generation before a concrete record exists: `mutation.unsafe(...)`.

Each exception is visible at the export. No quiet helper silently crosses
tenant boundaries.
