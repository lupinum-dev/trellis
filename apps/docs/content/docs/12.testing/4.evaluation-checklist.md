Use this page before treating a Trellis pilot as successful. The point is not to
prove that Trellis is magically safe. The point is to prove that your app is
using Trellis lanes, escape hatches, and agent tools intentionally.

## Minimum Pilot Checks

| Risk                | Required proof                                                              | Good evidence                                                                                            |
| ------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Anonymous access    | Anonymous callers cannot read protected workspace data.                     | Unit or Convex test calls the protected query without identity and receives a denial.                    |
| Role boundary       | Viewer or read-only roles cannot write.                                     | Test calls the mutation as a viewer and asserts denial.                                                  |
| Record boundary     | Members cannot modify records outside their authorization boundary.         | Own-record write passes; other-record write fails.                                                       |
| Tenant boundary     | Cross-workspace IDs are rejected.                                           | Test passes a valid record ID from another workspace and asserts denial or empty result.                 |
| Forged tenant input | `workspaceId` args do not override backend appIdentity.                     | Test sends another workspace ID and proves the handler derives or validates tenant state on the backend. |
| Frontend projection | UI `_can` state is not authorization.                                       | Test calls the backend directly and proves forbidden writes fail even if UI state is ignored.            |
| Destructive work    | Destructive operations cannot execute without confirmation.                 | Preview/confirm/execute test rejects missing, expired, reused, or mismatched confirmation.               |
| Webhooks            | Duplicate deliveries are idempotent.                                        | Repeated delivery ID does not duplicate the domain write.                                                |
| Forwarding          | Expired or forged forwarding evidence fails.                                | Test rejects expired envelope, wrong workspace, wrong args hash, or bad signature.                       |
| MCP tools           | Agent tools enforce the same backend permissions as browser/server callers. | MCP tool test uses a denied caller and asserts the backend permission failure.                           |

If the app does not use one of these paths, mark the row not applicable. Do not
delete the row from the pilot notes; future reviewers need to know it was
intentionally absent.

## Production Security Review

| Area                  | Review question                                                                             | Proof path                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `public` lanes        | Is the data or action genuinely public?                                                     | Manual review plus tests for protected alternatives where needed.                              |
| `publicWrite`         | Is the write operation-backed, narrow, and intentional?                                     | Escape-hatch inventory, operation id, explicit reason, write test.                             |
| `crossTenant`         | Are tables declared and methods narrow?                                                     | Doctor/inventory location plus test for allowed and disallowed tenants.                        |
| `unsafe` lanes        | Is the handler-level bypass unavoidable?                                                    | Typed permit, reason, scope, reviewer metadata where available.                                |
| Server `auth: 'none'` | Is the target public or does the route own verified transport proof?                        | Doctor inventory, reason, webhook/HMAC or bearer validation test.                              |
| Webhook HMAC          | Does verification use timestamp, delivery ID, raw body, and timing-safe compare?            | Unit test for missing secret, invalid signature, stale timestamp, duplicate delivery.          |
| Forwarding envelope   | Does it bind function ref, transport, purpose, args hash, TTL, and replay/JTI?              | Envelope tests and backend revalidation of service/user/workspace binding.                     |
| Confirmation token    | Is the token hashed, scoped, expiring, single-use, and args/preview-bound?                  | Confirmation tests for missing, expired, reused, wrong operation, wrong path, mismatched args. |
| MCP bearer keys       | Are keys hashed, revocable, and bound to user/workspace?                                    | Middleware tests and Convex validation tests.                                                  |
| MCP rate limiting     | Do rate-limited tools use a distributed store in production?                                | `trellis doctor --production` finding or explicit deployment review.                           |
| Service callers       | Are tables, tenant derivation, actingFor rules, replay mode, and audit metadata restricted? | Doctor/inventory finding plus service-subject tests.                                           |

## Doctor, Lint, Test, Or Manual Review

Every checklist item must map to one of these proof types:

- **Test**: the preferred proof for auth, tenant, role, webhook, forwarding, MCP,
  and destructive-operation behavior.
- **Doctor**: the preferred proof for configuration, inventory, weak keys,
  missing rate-limit stores, unsafe paths, and starter shape.
- **Lint**: useful for local source patterns that should never appear.
- **Manual review**: acceptable only when static tooling cannot reliably prove
  intent. Manual-review rows still need file locations and a written reason.

## When To Stop Adoption

Stop the pilot and simplify if:

- the team cannot explain which backend handler denies a forbidden action
- `workspaceId` or identity-shaped args become a frontend source of authority
- MCP tools start calling app writes outside operation-backed flows
- `auth: 'none'` appears as a workaround for missing identity
- escape hatches appear without explicit reasons and tests
- the smaller lane would satisfy the product

Trellis adoption is successful when the chosen lane is understandable and the
risky paths are proven. It is not successful just because the generated app
runs.
