Trellis can render a protected page with real auth and real Convex data before the browser takes over.

```ts [app/pages/tasks.vue]
const { data: tasks } = await useConvexQuery(api.tasks.list, { status: 'active' })
```

The same composable runs through SSR, hydrates on the client, then stays live through the Convex subscription. You do not need a separate fetch path just because the first render happened on the server.

## What SSR does

When `auth.enabled` is on, the Nitro server plugin runs before Vue renders the page:

1. Read the Better Auth session cookie from the request.
2. Exchange it for a Convex JWT.
3. Put the token and user state into Nuxt state for hydration.

That is why `isAuthenticated` can be true on first paint. The server already resolved the session, and the client receives that answer during hydration.

## Why protected pages do not flash

Without SSR auth, a protected page usually has three bad choices:

- render first, then redirect after the client checks auth
- block rendering until the client finishes checking auth
- guess from a cookie

Trellis avoids that by deciding on the server:

- authenticated: render the page
- unauthenticated: redirect before render
- misconfigured: fail loudly in development

The browser hydrates the result. It does not need to guess.

## How queries fit in

`useConvexQuery` is SSR-aware by default:

1. SSR awaits the first value and renders HTML with data.
2. The client hydrates with that same state.
3. The live Convex subscription takes over.

::note
If a query should not run during SSR, pass `server: false`. That is useful for non-critical dashboards, activity feeds, or browser-only data. See [Queries](/docs/data-fetching/queries#skip-ssr-for-non-critical-data).
::

## Auth readiness is not permission readiness

This is the common mistake.

SSR can know who is signed in before your app has loaded everything it needs for permissions.

Two things happen separately:

- `useConvexAuth()` tells you whether the browser request has a signed-in [caller](/docs/concepts/glossary#caller).
- `useAccess()` and your backend queries tell you what that caller can do as an [appIdentity](/docs/concepts/glossary#appIdentity).

A valid session can exist before the mirrored `users` row, access context, or workspace membership has loaded. Do not treat auth readiness as permission readiness.

::warning
Use `useConvexAuth()` for auth state. Use `useAccess()` for permission state. Mixing them is how a page tries to read permissions with a null context.
::

## Misconfiguration should be loud

In development, SSR auth failures should show up as errors. A quiet anonymous fallback hides the real problem.

Common causes:

- wrong `SITE_URL`
- wrong `CONVEX_SITE_URL` for a custom HTTP Actions domain
- Better Auth routes missing from `convex/http.ts`
- `BETTER_AUTH_SECRET` mismatch between local env and Convex

Run [`trellis doctor`](/docs/auth-security/auth-troubleshooting) before debugging the UI. It checks these problems directly.

## Optional SSR auth cache

Token exchange is cheap, but not free. Under load, you can cache it:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  trellis: {
    auth: {
      cache: { enabled: true, ttl: 60 },
    },
  },
})
```

Leave it off unless you have a real reason. The cache trades a small correctness window for fewer SSR round trips. That can make sense in production traffic. It usually does not help local development.

## SSR is not a server route

Two Trellis paths run on the server:

- SSR page rendering: Nuxt renders a page for a browser request.
- Nitro server routes: your own `/api/*` handlers call Convex from the server.

They are related, but not the same flow. If you are writing a `/api/*` handler, read [Server routes](/docs/server-side/server-routes).

## Common pitfalls

- Using auth state as a stand-in for permission readiness.
- Chasing a protected-page flash in the UI instead of fixing SSR auth.
- Enabling auth cache in development to hide slow or broken sign-in.
- Treating SSR rendering and server helpers as the same thing.
