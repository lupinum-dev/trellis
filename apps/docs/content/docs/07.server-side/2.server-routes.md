Call a Convex function from a Nitro `/api/*` route — same function, same appIdentity, same backend authorization, different transport. The per-call helpers make the auth mode explicit so the route can't accidentally forge permissions.

```ts [server/api/tasks/export.get.ts]
import { api } from '#trellis/api'

export default defineEventHandler(async (event) => {
  const projectId = getQuery(event).projectId as string

  return await serverConvexQuery(
    event,
    api.tasks.listForExport,
    { projectId },
    { auth: 'required' },
  )
})
```

Four helpers, one shape: `serverConvexQuery`, `serverConvexMutation`, `serverConvexAction`, and `createServerConvexCaller` for multi-call routes.

## Pick the auth mode deliberately

The per-call helpers support an `auth` option. If you omit it, they default to `auto`. In practice, you should still choose the trust boundary deliberately:

| Mode                    | Who's the caller                                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`                  | Use request auth when available, fall through if not                                                                                   |
| `required`              | Fail if request auth can't be resolved                                                                                                 |
| `none`                  | Never attach auth; use for genuinely public handlers or explicitly reviewed route-owned transport proof                                |
| `transportProof.*(...)` | Inject [identity-forwarding](/docs/server-side/webhooks-and-identity-forwarding) identity only through verifier-produced proof objects |

::warning
Don't reach for transport proof auth to "just make it work." It forwards server-owned identity — use it only for server-to-server flows where the signal is real and replay-safe. For user-initiated routes, use `required`.
::

::caution
Treat `auth: 'none'` as an escape hatch. If the target is not genuinely public,
the route needs an explicit reason, transport proof, idempotency where relevant,
and a test. See [Escape hatches and raw access](/docs/permissions/cross-scope-and-raw-access).
::

## Mutation from a Nitro route

Writes look the same. This example is an identity-forwarding flow (webhook, admin tool — not a user request):

```ts [server/api/internal/tasks.post.ts]
import { createError } from 'h3'
import { api } from '#trellis/api'
import {
  domainIdempotency,
  requireDelegationBinding,
  serverConvexMutation,
  transportProof,
} from '#trellis/server'

function requireInternalServiceSecret() {
  const secret = process.env.INTERNAL_TASK_SERVICE_SECRET
  if (!secret) {
    throw createError({
      statusCode: 500,
      statusMessage: 'INTERNAL_TASK_SERVICE_SECRET is not configured.',
    })
  }
  return secret
}

export default defineEventHandler(async (event) => {
  requireInternalServiceSecret()
  const body = await readBody(event)
  const target = api.tasks.create

  return await serverConvexMutation(
    event,
    target,
    {
      projectId: body.projectId,
      title: body.title,
    },
    {
      auth: transportProof.server({
        caller: {
          kind: 'service',
          serviceId: 'internal-task-service',
          subject: 'service:internal-task-service',
        },
        actingFor: requireDelegationBinding({
          serviceId: 'internal-task-service',
          targetUserId: body.targetUserId,
          workspaceId: body.workspaceId,
          purpose: 'create-task',
          grantSource: 'workspace-service-policy',
          expiresAt: Date.now() + 5 * 60 * 1000,
        }),
        replay: domainIdempotency({
          key: body.eventId,
          target,
        }),
      }),
    },
  )
})
```

The route-created binding is not enough by itself. The target Convex handler's
`actingFor` resolver must revalidate the binding against backend state such as
workspace membership, account connection, service policy, or an explicit grant.

## Multi-call routes: one caller, many calls

When a single Nitro request needs several Convex calls, create a request-scoped caller instead of passing `event` and auth every time:

```ts [server/api/dashboard.get.ts]
import { api } from '#trellis/api'

export default defineEventHandler(async (event) => {
  const convex = createServerConvexCaller(event, { auth: 'required' })

  const [summary, activity, notifications] = await Promise.all([
    convex.query(api.dashboard.summary, {}),
    convex.query(api.dashboard.recentActivity, {}),
    convex.query(api.notifications.recent, {}),
  ])

  return { summary, activity, notifications }
})
```

::note
The caller is bound to this request. Don't cache it across requests — the event and auth are per-request, and a leaked caller would serve the wrong user.
::

## Passing `event` matters

The helpers need the H3 event to read auth from the request. Pass it explicitly when you're inside a normal route. If you try to call them somewhere Nitro request context isn't available, they throw a clear error — which is the right behavior. A helper that invented request state silently would be worse than one that fails.

## Errors include helper context

If a call fails, Trellis reports which helper was used, the function path, and the auth mode. Debugging a generic `fetch('/api/query')` wrapper means guessing; these errors tell you the exact shape of the failing call.

## What goes in the Nitro route vs. the Convex handler

Nitro routes should stay thin. They exist to:

- validate HTTP input (body shape, query params);
- pick the right auth mode;
- call the existing Convex function;
- shape the HTTP response.

For that edge validation, prefer hand-authored Zod schemas next to the route or feature that owns the HTTP boundary. Promote a shape into `shared/features/` only when Convex, Nuxt, and MCP intentionally share the same input contract. The route owns HTTP parsing; the Convex handler owns the backend runtime contract. Re-validating at the Convex boundary is intentional.

They **should not** duplicate business authorization. That lives in the Convex handler's lane, permission, load, and authorize phases, where every transport path enforces it. If you find yourself re-checking permissions in the Nitro route, move the check into the Convex handler instead.

## Common pitfalls

- Relying on the default `auth: 'auto'` when the route really needs `required` or a transport proof.
- Using transport proof auth for user-initiated routes. That's a way to ship auth bypasses.
- Duplicating permission checks in the Nitro layer. One source of truth (the Convex handler).
- Caching a `createServerConvexCaller` across requests.
