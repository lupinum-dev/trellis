Pick the smallest example that proves the boundary you actually need.

Do not copy the largest app because it looks more complete. Larger examples carry more rules, files, and setup. That is useful only when your app needs those rules too.

## Read these first

Start with the examples in this order:

1. [`01-public-todo`][01-public-todo]
2. [`02-auth-todo`][02-auth-todo]
3. [`03-team-workspace`][03-team-workspace]
4. [`04-saas-platform`][04-saas-platform]

Each one adds one main layer:

- `01` proves public Convex queries and mutations through Trellis.
- `02` adds Better Auth and per-user data.
- `03` adds workspaces, roles, permissions, and tenant isolation.
- `04` adds pagination, uploads, Nitro routes, and practical SaaS flows.

Stop as soon as the example matches your app.

If agents are already part of the product, read `07-mcp-reference` after the workspace boundary is clear. Do not evaluate MCP by bolting a tool onto a public toy app.

## Match the example to the problem

| Example                                          | Open it when you need                         | What it proves                             |
| ------------------------------------------------ | --------------------------------------------- | ------------------------------------------ |
| [`01-public-todo`][01-public-todo]               | Public-only queries and mutations             | Smallest useful Trellis baseline           |
| [`02-auth-todo`][02-auth-todo]                   | Sign-in and personal ownership                | Auth plus app-owned users, no tenancy      |
| [`03-team-workspace`][03-team-workspace]         | Roles, permissions, or tenant boundaries      | Workspace data with backend rules          |
| [`04-saas-platform`][04-saas-platform]           | Pagination, uploads, admin flows, SaaS depth  | A richer workspace app                     |
| [`05-visibility-access`][05-visibility-access]   | Visibility, redaction, enrollment, or sharing | Advanced access-control patterns           |
| [`06-multi-workspace`][06-multi-workspace]       | Workspace switching or operator views         | Multi-workspace membership                 |
| [`07-mcp-reference`][07-mcp-reference]           | Workspace MCP agents                          | Read tools and operation-backed writes     |
| [`08-component-mini-cms`][08-component-mini-cms] | Packaged integration boundaries               | Component bridge plus MCP over bridge refs |

## Patterns after the first ladder

Use the later examples as pattern references, not starter apps:

- [`04-saas-platform`][04-saas-platform]: pagination, uploads, Nitro routes, admin workflows
- [`05-visibility-access`][05-visibility-access]: visibility and sharing rules
- [`06-multi-workspace`][06-multi-workspace]: workspace switching and operator views
- [`07-mcp-reference`][07-mcp-reference]: workspace MCP after roles and isolation are already clear
- [`08-component-mini-cms`][08-component-mini-cms]: package integration and bridge refs

The maintained examples use the same folders when those parts exist:

- `convex/features/*` for backend feature code
- `shared/features/*` for input contracts shared by Convex, Nuxt, and MCP
- `app/features/*` for feature UI
- `convex/permissions/context.ts` for permission projection into the UI

## Source of truth

`examples/` is the maintained public example set.

Use it for:

- first-reader learning paths
- docs code references
- patterns worth copying into real apps

`labs/` is archived or exploratory. Do not copy from it unless a maintainer points you there.

## Read before you copy

Copy patterns, not whole apps.

1. Choose the smallest matching example.
2. Read the files that define the boundary you need.
3. Copy only that pattern.
4. Stop before unrelated auth, workspace, upload, bridge, or MCP code comes along for the ride.
