Trellis is for Nuxt apps that use Convex as the backend and need the same rules to work across more than one place.

That usually means:

- browser pages
- server routes
- signed-in users
- workspace data
- permissions
- webhooks
- MCP tools

The main idea is simple:

Put the important rules in Convex. Let every caller go through that same backend path.

Do not use Trellis if raw Nuxt + Convex is enough. Trellis is opinionated on purpose. It gives you a generated app layout, supported starter lanes, examples, doctor checks, and runtime checks. That is useful when your app will grow into auth, permissions, server routes, or agents. It is too much if you only need a tiny public app.

If you are still deciding, read [Adoption decision](/docs/getting-started/adoption-decision) first.

## The fastest path

Create a new app:

```bash [Terminal]
pnpm dlx @lupinum/trellis init my-app
```

Then run it:

```bash [Terminal]
cd my-app
pnpm install
pnpm dlx @lupinum/trellis doctor
pnpm dev:local
```

That is the first Trellis loop:

1. Generate the app.
2. Install dependencies.
3. Run doctor.
4. Start the local app.
5. Build one real feature before adding more layers.

Do not skip doctor. If the generated app is misconfigured, doctor usually points closer to the cause than a browser error or a stack trace.

## Start small

Trellis works best when you add features only when the app needs them.

Start public. Add auth when users are real. Add workspace when shared data is real. Add MCP when agents are real.

```bash [Terminal]
trellis add auth
trellis add workspace
trellis add mcp
```

These commands are a ladder, not random templates.

## Pick the right lane

| Lane            | Use it when                                                  | Do not use it when                          |
| --------------- | ------------------------------------------------------------ | ------------------------------------------- |
| `public`        | The app has public data and no sign-in flow yet.             | You already need users, workspaces, or MCP. |
| `personal`      | The app needs signed-in users, but no shared workspace data. | You need team roles or tenant boundaries.   |
| `workspace`     | The app needs shared data, roles, or workspace isolation.    | Each user only owns their own data.         |
| `workspace-mcp` | Agents are already part of the product.                      | You are only curious about MCP.             |

If you are unsure, choose the smaller lane.

A smaller app is easier to understand. You can always add auth, workspace, and MCP later. Starting too high gives you files, rules, and concepts you do not need yet.

## What each lane adds

### Public

Use this for the smallest useful app.

You get public queries and mutations, a feature-first file layout, and a working live data path.

Good first goal: build one todo list. Add one item. See the list update without writing refetch code.

### Personal

Use this when users sign in and each user owns their own data.

You get Better Auth, authenticated handlers, and app-owned users.

Good first goal: sign in as one user, create a todo, then sign in as another user and confirm the first user's todo is not visible.

### Workspace

Use this when data belongs to a workspace, team, tenant, or organization.

You get roles, workspace identity, backend permissions, and tenant isolation patterns.

Good first goal: create one workspace rule. Prove a viewer cannot write. Prove another workspace cannot read the record.

### Workspace MCP

Use this when MCP agents are part of the product from the start.

You get the workspace model plus MCP bearer auth, scoped tools, operation-backed writes, and destructive safety patterns.

Good first goal: expose one read-only tool first. Then expose a write through an operation. Do destructive tools last.

## The day-one mental model

You only need three folders at first:

```txt [Generated app]
shared/features/
convex/features/
app/features/
```

Use them like this:

| Folder                    | What goes there                                                  |
| ------------------------- | ---------------------------------------------------------------- |
| `shared/features/<name>/` | Input contracts shared by Convex, Nuxt, and MCP.                 |
| `convex/features/<name>/` | Backend schema, queries, mutations, permissions, and operations. |
| `app/features/<name>/`    | Vue components and UI code for that feature.                     |

Keep route files thin. Put feature UI in `app/features`. Put backend rules in `convex/features`. Put shared input shapes in `shared/features`.

That layout is not decoration. It is how Trellis keeps apps easy to navigate after they grow.

## What Trellis handles

Trellis handles the repeated framework wiring:

- Nuxt module setup
- Convex client setup
- SSR-aware queries
- live subscriptions
- mutation state
- Better Auth integration
- auth refresh after sign-in
- permission projection into the UI
- server helpers for Nitro routes
- MCP tool projection
- doctor checks for common setup mistakes

You still own the product rules:

- what tables exist
- what a user means in your app
- what a workspace means
- who can create, update, delete, invite, publish, revoke, or export
- what a destructive action should preview before it runs

Trellis gives you the path. It does not invent your business logic.

## What success looks like

Your first success should be boring:

1. The app starts.
2. Doctor passes.
3. One page reads from Convex.
4. One mutation writes to Convex.
5. The page updates without a manual refresh.

That is enough for the first pass.

Do not start by wiring every feature. Do not read every concept page first. Do not copy the workspace example unless your app already needs workspaces.

Build the smallest real slice, then move up the ladder.
