Use Trellis when one backend rule system needs to serve more than the browser.

That means the same Convex path should protect browser UI, server routes, webhooks, and maybe MCP tools. If your app does not need that, raw Nuxt + Convex may be the better choice.

Trellis is a framework, not a neutral helper. It gives you a maintained app shape, starter lanes, examples, code generation, lint rules, and `doctor`. In return, you accept its structure.

## The short answer

Use Trellis when the product already points at this stack:

- Nuxt for the app
- Convex for the backend
- Better Auth when identity is needed
- backend-owned permissions when the UI must not invent access rules
- server routes or webhooks that need the same authorization checks as the browser
- MCP tools when agents are already part of the product

Skip Trellis when the app is tiny, public-only, short-lived, or you want full freedom to invent the app shape yourself.

## Use Trellis if

- You are already choosing Nuxt + Convex.
- You want one backend path for browser UI, Nitro routes, webhooks, and MCP tools.
- Tenant isolation, roles, permission projection, or destructive workflows are real product requirements.
- Agent workflows are part of the product, not a demo bolted onto an API route.
- You want the CLI, examples, lint rules, and `doctor` to keep the team on one shape.

## Skip Trellis if

- The app is a static site, a tiny prototype, or a one-off internal tool.
- Raw Convex queries and mutations are enough.
- You want an unopinionated helper library.
- You plan to throw away the canonical feature layout on day one.
- The team does not want backend-owned authorization.
- The app has no shared auth, permission, server-boundary, webhook, or MCP convention to enforce.

## Choose your starting lane

| Lane            | Start here when                                                           | Do not start here when                         |
| --------------- | ------------------------------------------------------------------------- | ---------------------------------------------- |
| `public`        | The app has public data and no signed-in workflow yet.                    | You already need users, workspaces, or agents. |
| `personal`      | The app needs signed-in users but no tenant roles.                        | You need shared workspaces or role boundaries. |
| `workspace`     | The app needs tenant isolation, roles, and backend permission projection. | The app has no shared data boundary.           |
| `workspace-mcp` | MCP agents are already part of the product.                               | You are only curious about MCP.                |

If you are unsure, choose the smaller lane.

Starting too high gives you files and rules you do not need yet. Starting too low is fine as long as the next layer is a real product need.

## Evaluate MCP first when agents are real

MCP is first-class in Trellis. That does not mean every app starts with MCP. It means agent-enabled apps should not create a separate authorization model just for tools.

Start with `workspace-mcp` when you need to answer questions like:

- Can a user or service safely delegate a scoped agent?
- Can a tool expose only what the caller may use?
- Can destructive agent writes require preview and confirmation?
- Can MCP bearer keys be hashed, revoked, and tied back to a user or workspace?
- Can webhooks, server routes, browser UI, and MCP tools share one backend rule path?

If those are your real questions, evaluating only the public or personal lane will undersell Trellis.

## One-afternoon evaluation

Do not evaluate Trellis by reading every page.

1. Pick the smallest lane that matches the product.
2. Generate the app.
3. Run `pnpm install`.
4. Run `pnpm dlx @lupinum/trellis doctor`.
5. Start the local app.
6. Build one real vertical slice.
7. Run the checks from the [Evaluation checklist](/docs/testing/evaluation-checklist).

Stop early if the team cannot explain which backend handler enforces authorization. That is the point of the framework.

## One-week pilot

A serious pilot should include only the boundaries your product actually has.

For a workspace app, prove:

- one tenant-scoped resource
- one role-based rule
- one own-record versus other-record check
- one cross-workspace denial test

Add a server route or webhook only if the product has that boundary.

Add an operation-backed destructive flow only if destructive work exists.

Add one MCP tool only if agent access is part of the product.

## Decision outcomes

Adopt Trellis when the pilot proves that the framework keeps copied authorization rules out of the app and the team understands the lane it chose.

Use raw Nuxt + Convex when Trellis feels like policy architecture before the product has policy problems.

Keep MCP first-class when agents are part of the product, but do not create a parallel agent-only authorization model. MCP tools should use the same backend rules as browser and server callers.
