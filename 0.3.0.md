# Trellis 0.3.0 Architecture Scope

Status: Aggressively reviewed 0.3.0 scope
Date: 2026-06-04
Owner: Matthias
Source material:

- `auth-review-rfc.md`
- `library-review-state.md`
- Fresh source probes on 2026-06-04
- Security, API/DX, and verification subagent architecture passes
- Four external LLM architecture reviews provided after the first 0.3.0 draft

## Purpose

Trellis 0.3.0 should not be a patch release that tapes over every individual
auth finding. It should be a hard architecture reset for the security-sensitive
parts of the library.

The target shape is:

- easy to read
- explicit over magical
- hard to use incorrectly
- friendly to agents that write code by following local examples
- reviewable by humans who need to see auth decisions close to business code

Writing three explicit lines is acceptable if it removes ambiguity. The goal is
not fewer keystrokes. The goal is fewer footguns.

## Current Evidence

The review found 58 open auth/security findings. A fresh ledger check confirmed
the current markdown contains F-AUTH-01 through F-AUTH-58 with no missing IDs.

Fresh source probes confirmed the current architecture still exposes the risky
shapes that caused the review findings:

- `src/runtime/functions/index.ts` attaches `Symbol('trellisUnsafeDb')` directly
  to handler-visible `ctx.db`.
- `ctx.db.escapeIsolation(...)` is available on normal decorated query/mutation
  DB contexts.
- `.protected(...)` requires a `guard` property but does not reject `guard:
open`.
- `runCheck(...)` returns arbitrary function results as booleans.
- `authRequired` is implemented as an inert `true` check and is special-cased
  only by the structured handler guard phase.
- `@lupinum/trellis/server` exports `delegateToUser` and
  `readSharedSecretWebhookBody`.
- `delegateToUser` accepts `allow: boolean | (() => boolean)`.
- Shared-secret webhook verification compares one header to a static secret and
  does not bind raw body, timestamp, or delivery id.
- HMAC webhook idempotency is consumed before parsing succeeds.
- `@lupinum/trellis/mcp` exports `stampMcpToolSafety`.
- `@lupinum/trellis/mcp/advanced` exports raw toolkit write-capable helpers.
- `@lupinum/trellis/backend` exports raw identity-forwarding primitives.
- `createMcpConvexCaller(...)` signs trusted calls through the server transport
  lane.
- `useMcpSession(...)` scopes session storage by role/user/workspace but not by
  bearer key id.
- Maintained examples still show production-copyable unsafe patterns:
  shared-secret trusted webhooks, `auth: 'trusted'`, unconditional
  `delegateToUser({ allow: true })`, direct MCP safety stamping, and a public
  multi-workspace seed mutation.
- `package.json` has no focused `test:security` command in `pnpm check`.

This means the 0.3.0 design should remove normal access to these primitives
instead of wrapping them with more warnings.

## Trust Model

Backend Convex handlers are the enforcement boundary.

Everything else is orchestration:

- Nuxt route protection is UX and flash prevention, not authorization.
- Nuxt server routes can verify an inbound request, but they cannot mint trust
  from string literals.
- MCP is transport and presentation, not authorization.
- Better Auth is the authoritative human session source.
- Trellis client auth state is derived from Better Auth and Convex token
  exchange state.
- Identity forwarding proves transport facts. It does not authorize the target
  handler by itself.

Identity forwarding proves:

- issuer
- audience
- function ref
- args hash
- purpose
- transport
- caller
- optional representation subject
- issued-at
- expires-at
- replay key

Backend guards still decide whether the caller may do the work.

## 0.3.0 Design Principles

1. Delete unsafe normal APIs before adding new ones.
2. Make auth intent visible at the backend handler or operation definition.
3. Keep one authorization evaluator for guards, permissions, projection, and
   MCP visibility.
4. Treat examples and starters as production templates.
5. Make trust and delegation evidence values, not string or boolean options.
6. Make all write replay behavior explicit.
7. Make public exports exact and hostile to accidental unsafe extras.
8. Prefer hard cutovers for 0.3.0.

## Aggressive Review Outcome

The proposal is directionally right, but the first draft overcorrected in two
places:

1. It treated `trusted` as a backend handler lane. That is worse than the
   current model because it makes transport verification look like
   authorization. Trusted forwarding should produce a signed caller/service
   proof for an existing backend lane. It should not be a lane itself.
2. It risked adding a broad cross-tenant capability DSL. That can become
   `escapeIsolation(...)` with nicer syntax if it is too generic. Cross-tenant
   capability must stay narrow, table-scoped, reasoned, and statically visible.

The good tradeoffs are worth keeping:

- Breaking unsafe public APIs is worth it because 0.2.x already proved the
  easier path is copyable and dangerous.
- More explicit route/MCP code is worth it because agents and humans can review
  concrete verifier, idempotency, permission, and delegation evidence.
- A focused `test:security` gate is worth it because the current broad checks
  miss critical auth regressions.
- Production-safe examples are worth making less tiny because examples are
  effectively generators for future apps.

The costs are real:

- 0.3.0 will be a breaking release.
- Simple apps will write more boilerplate for server routes and destructive
  writes.
- MCP write tooling becomes less flexible.
- Cross-tenant workflows need more upfront modeling.
- The security contract adds another generated artifact to maintain.

The tradeoff is still worth it because the alternative is a library that is
pleasant to start with but easy to deploy insecurely.

This is not the final Trellis forever. It is the security foundation release.
After 0.3.0, Trellis can add ergonomic helpers only when they compile down to
the same explicit backend-owned authority model.

External review synthesis:

- Accepted: `service` must not become ambient backend authority. It ships only
  with a concrete service-subject contract; otherwise delay it.
- Accepted: cross-tenant capabilities must not expose a generic DB/query
  builder. They must be named, read-only by default, table/index scoped,
  subject-bound, inventoried, and test-backed.
- Accepted: operations are not merely "preferred" for high-risk writes. They
  are mandatory for MCP writes, destructive writes, trusted server-route writes,
  and external-side-effect writes unless a named integration write declares
  domain idempotency.
- Accepted: webhook idempotency cannot be a route-side consume followed by a
  fallible backend dispatch. The delivery claim/complete/fail state must be
  backend/domain-atomic, or at least recoverable.
- Accepted: delegation evidence needs concrete fields and backend
  revalidation. A route-created representation object is not enough.
- Accepted: direct MCP mutation tools should be deleted from first-reader
  0.3.0 APIs. If an advanced path survives, it must consume backend-owned
  operation descriptors, never MCP-local safety metadata.
- Accepted: the generated security contract should start as a small exact MVP,
  not a broad introspection system.
- Accepted: real consumer migration pressure matters. Ginko CMS and
  shadcn-style Trellis templates are proof that examples get copied; 0.3.0
  needs migration gates, not just library tests.

Final approval feedback:

- Approved as the 0.3.0 implementation baseline, not as release approval.
- Keep Phase 0 small and blocking: source-policy checks and public export
  removals land before new abstractions.
- If the service-subject contract is not fully enforced, delay the `service`
  lane.
- Do not keep direct MCP mutation as a convenient fallback. Any advanced write
  path must be operation-descriptor backed or absent.
- Do not let replay/idempotency become route-side bookkeeping.
- Do not let the security contract accept manual approvals without matching
  negative tests.
- Define `public-safe DB facade` concretely before coding the new lanes.
- For domain-idempotent trusted writes, the backend handler or operation
  declares and enforces the idempotency key. The server route proof object alone
  is insufficient.
- Run consumer migration gates before calling 0.3.0 viable.

## Core Architecture

### 1. Capability-Typed Handler Lanes

Replace the current broad `public/protected/unsafe` mental model with explicit
lanes that shape the context a handler receives.

Target API:

```ts
export const listPosts = query.public({
  handler: async (ctx, args) => {
    return await ctx.db.query('posts').collect()
  },
})

export const createPersonalTodo = mutation.authenticated({
  handler: async (ctx, args) => {
    return await ctx.db.insert('todos', {
      userId: ctx.identity.userId,
      title: args.title,
    })
  },
})

export const updateWorkspacePost = mutation.workspace({
  permission: posts.update,
  load: async (ctx, args) => {
    return { post: await ctx.db.get(args.id) }
  },
  authorize: ({ loaded, identity }) => loaded.post.ownerId === identity.userId,
  handler: async (ctx, args, loaded) => {
    await ctx.db.patch(loaded.post._id, { title: args.title })
  },
})
```

Required lanes:

| Lane            | Auth source                                    | Context authority                      | Normal use                                               |
| --------------- | ---------------------------------------------- | -------------------------------------- | -------------------------------------------------------- |
| `public`        | none                                           | public-safe DB facade only             | public reads and unauthenticated entrypoints             |
| `authenticated` | Better Auth/app identity                       | user identity, no workspace assumption | onboarding, personal data, account flows                 |
| `workspace`     | app identity plus workspace                    | tenant-scoped DB facade                | normal SaaS app reads/writes                             |
| `service`       | internal service subject with service contract | explicitly scoped service facade       | backend jobs and verified integration work               |
| `unsafe`        | explicit unsafe permit                         | raw or cross-scope authority           | tests, migrations, and reviewed framework internals only |

Rules:

- `public` does not accept `guard`.
- `authenticated` replaces `authRequired` as a normal public concept.
- `workspace` requires either a permission or a named policy.
- `service` is for backend-owned subjects only; external webhooks reach it
  through a verifier-produced trusted caller proof.
- `service` ships only if the service-subject contract below is implemented.
  Otherwise delay it and keep service work behind explicitly reviewed internal
  functions for the first 0.3.0 cut.
- `guard: open` is not valid outside `public`.
- Normal lanes do not receive raw DB.
- Normal lanes do not receive `escapeIsolation`.
- Cross-tenant work is not a method hidden on `ctx.db`; it is a lane/capability
  choice reviewers can see at the export.
- `trusted` is not a handler lane. It is a transport proof used by server/MCP
  callers to invoke `authenticated`, `workspace`, or `service` handlers as a
  verified subject.
- Do not add an `admin` lane until there is a concrete generic admin use case.
  Prefer `service` plus explicit permissions/capabilities for now.

Decision:

Delete `authRequired` from the normal first-reader API. If a sentinel remains
internally, it must not be usable as a permission/check value.

#### Lane Context Contract

The lane set is only useful if each lane has precise context authority.

| Lane            | `ctx.identity`                   | `ctx.db`                             | Extra context                       | Forbidden                                                     |
| --------------- | -------------------------------- | ------------------------------------ | ----------------------------------- | ------------------------------------------------------------- |
| `public`        | absent                           | public-safe facade                   | none                                | app identity, workspace identity, raw DB, cross-tenant access |
| `authenticated` | user/app identity                | personal/shared-table facade         | onboarding capability when declared | workspace DB by default, raw DB, cross-tenant access          |
| `workspace`     | user/app identity plus workspace | tenant-scoped facade                 | permission/policy result            | raw DB, undeclared cross-tenant access                        |
| `service`       | service subject                  | service-scoped facade from contract  | service capability, audit metadata  | ambient all-table access, undeclared acting-for               |
| `unsafe`        | explicit permit subject          | permit-scoped raw/cross-scope access | permit metadata                     | production use without reviewed permit                        |

`authenticated` must define which tables are reachable. It is not a weak
workspace lane. Personal/account/onboarding tables are allowed; workspace data
requires `workspace` or a named onboarding capability.

`public-safe facade` must be defined before implementation. At minimum it means:

- no raw DB reference
- no tenant-scoped write access
- no cross-tenant access
- no service-table access
- no user/email lookup that leaks private identity data
- no shared-table access unless the table has an explicit public-read policy
- no writes except explicitly declared public-safe insert operations with
  validation, rate limiting, and abuse tests

#### Service Subject Contract

`service` is the most likely new footgun. It must be specified before it ships.

Required service metadata:

- `serviceId`
- issuer/source, for example `internalJob`, `verifiedWebhook`, or
  `scheduledTask`
- purpose
- allowed function refs or operation ids
- allowed tables, if the service receives DB access
- tenant mode: `none`, `singleWorkspace`, or explicit reviewed `multiWorkspace`
- replay mode for writes
- whether acting-for is allowed, default `false`
- audit event name and correlation id

Rules:

- A verified webhook does not become broad service authority. It becomes a
  service subject for one declared operation/purpose.
- `service` cannot represent a user unless it carries delegation evidence that
  the target backend handler can revalidate.
- External service writes must be operation-backed or declared as idempotent
  integration writes.
- Production doctor fails any service subject without scope, replay mode for
  writes, and audit metadata.

#### Unsafe Contract

`unsafe` is not a first-reader lane.

Rules:

- No maintained example uses `unsafe` for normal product behavior.
- Production doctor fails unsafe use by default.
- Every unsafe permit has reason, owner, scope, expiry or review cadence, and
  matching negative tests.
- Unsafe helpers are never imported from first-reader public barrels.
- If a migration requires unsafe access, the migration file says so at the
  export, not hidden inside a helper.

### 2. One Strict Authorization Evaluator

Current issue class: async/truthy/non-boolean guards and duplicate permission
keys create fail-open behavior and projection drift.

0.3.0 should have one evaluator used by:

- handler lanes
- permissions
- composed policies
- `can`
- `enforce`
- access projection
- operation descriptors
- MCP visibility

Evaluator rules:

- Only exact `true` and exact `false` are valid check results.
- Promise-like values throw or deny.
- Objects, strings, numbers, arrays, and functions returned from checks throw or
  deny.
- Thrown errors deny.
- Async authorization belongs in `load` or `authorize`, not guard checks.
- Permission keys are globally unique across the app graph.
- Duplicate permission keys fail in feature composition, access context,
  codegen, doctor, and tests.

Target API:

```ts
export const posts = definePermissions({
  read: permission('posts.read', ({ role }) => role !== 'blocked'),
  update: permission('posts.update', ({ role }) => role === 'editor'),
})
```

Non-goal:

Do not add an async permission system unless it has one explicit execution
phase and one projection story. Mixing async checks into boolean projection is
the footgun.

### 3. Tenant Isolation By Construction

Current issue class: normal handler code can recover raw DB or call
`escapeIsolation`.

0.3.0 target:

- `ctx.db` is only a tenant/service-scoped facade.
- No hidden raw DB symbol is attached to handler-visible DB objects.
- `Reflect.ownKeys`, `Object.getOwnPropertySymbols`, descriptors, prototypes,
  and service wrappers cannot recover raw DB.
- Cross-tenant access is modeled as a separate capability.
- Shared tables require explicit global/shared-table policy.

Target shape:

```ts
export const listAccessibleWorkspaces = query.authenticated({
  crossTenant: membershipsForUserAcrossWorkspaces({
    reason: 'Resolve memberships for the signed-in user.',
    tables: ['memberships', 'workspaces'],
    subject: ({ identity }) => identity.userId,
  }),
  handler: async (ctx) => {
    return await ctx.crossTenant.listAccessibleWorkspaces()
  },
})
```

The important distinction: the capability is visible at the handler definition,
not hidden inside a helper that calls `ctx.db.escapeIsolation(...)`.

Rules:

- No normal lane exposes `escapeIsolation`.
- `unsafe` can expose special DB capabilities, but it must require typed permits
  and emit observability.
- Doctor fails public/protected cross-scope access without a reviewed
  capability.
- Shared table joins must either be tenant-bounded or declared as global lookup
  capabilities with negative tests.
- Cross-tenant helpers must be narrow and table/index scoped.
- Cross-tenant helpers are read-only by default.
- Cross-tenant writes require either an operation-backed workflow or an unsafe
  permit.
- Do not expose a generic cross-tenant DB facade, fluent query builder, or
  arbitrary `where` composition in 0.3.0.
- Every cross-tenant capability has subject binding, reason, allowed tables,
  allowed indexes/predicates, generated inventory, and at least one negative
  test proving an adjacent tenant/user cannot use it.

### 4. Operations Become The Write Contract

Current issue class: direct writes, MCP writes, and destructive flows can drift
from permission/safety/replay expectations.

0.3.0 target:

Operations are the write abstraction for high-risk write surfaces.

```ts
export const publishPage = operation.mutation({
  id: 'pages.publish',
  permission: pages.publish,
  handler: async (ctx, args) => {
    await ctx.db.patch(args.id, { status: 'published' })
  },
})

export const deleteRunbook = operation.destructive({
  id: 'runbooks.delete',
  permission: runbooks.delete,
  preview: async (ctx, args) => {
    return operationPreview({
      effects: [operationEffect.delete('runbook', args.id)],
    })
  },
  execute: async (ctx, args) => {
    await ctx.db.delete(args.id)
  },
})
```

Operation rules:

- Every write operation has a permission.
- Operation metadata derives from the backend definition only.
- MCP visibility derives from the same permission.
- Destructive operations require preview.
- Destructive execute requires backend replay redemption.
- Destructive execute writes durable audit rows.
- Tests must replay the same captured execute request and prove the handler is
  not reached twice.

Mandatory operation-backed surfaces:

- MCP writes
- destructive writes
- trusted server-route writes
- writes with external side effects
- writes exposed in maintained examples/starters

Direct `mutation.*` remains only for simple browser/backend-local writes that
have no external side effect, no destructive semantics, no MCP exposure, and no
trusted transport. Any exception must be explicit in source and fail production
doctor unless reviewed.

### 5. Trusted Writes Use Proof Objects

Current issue class: `{ auth: 'trusted' }` plus caller/actingFor options makes
trusted identity forwarding too easy to spell and too hard to review.

0.3.0 target:

Trusted calls require verifier-produced proof values. Trusted is call-side
transport state, not backend authority. Avoid user-authored `trusted*` literals;
the public API should pass opaque verifier-produced proof objects.

```ts
const delivery = await verifyHmacWebhookDelivery(event, {
  secret: env.LINEAR_WEBHOOK_SECRET,
  parse: linearWebhookSchema.parse,
})

await serverConvexMutation(
  event,
  api.webhooks.importLinearTask,
  {
    deliveryId: delivery.id,
    payload: delivery.body,
  },
  {
    auth: transportProof.webhook(delivery, {
      service: 'linear',
      replay: domainIdempotency({
        key: delivery.id,
        target: api.webhooks.importLinearTask,
      }),
    }),
  },
)
```

Rules:

- No raw `{ auth: 'trusted' }` string in app code.
- No forwarded caller without a trust proof.
- No handler may rely on "trusted" as the permission decision. The target
  handler still uses `authenticated`, `workspace`, or `service` authorization.
- No trusted mutation/action without idempotency or durable JTI redemption.
- Purpose is derived from the actual Convex helper operation and cannot be
  overridden per call.
- Transport is exact. If MCP is a real security boundary, MCP calls sign
  `transport: 'mcp'`; otherwise delete the unused MCP transport option.
- The proof object is branded/opaque and cannot be constructed from app
  literals.
- Proof fields include verifier kind, delivery id or JTI, issuer, subject,
  expiry, purpose, transport, target ref, args hash, and replay mode.

Trusted query:

- Signature, function, args hash, TTL, purpose, and transport binding are enough
  unless the query itself has side effects.

Trusted mutation/action:

- Must use one of:
  - app/domain idempotency key
  - backend JTI redemption before handler execution
  - destructive operation confirmation flow

#### Replay Store Contract

Replay behavior is an API contract, not prose.

Allowed replay modes:

- `domainIdempotency({ key, target })`
- `jtiRedemption({ store, ttl })`
- `operationConfirmation`

Backend replay records include:

- key or JTI
- target function or operation id
- purpose
- transport
- args hash
- issuer/subject
- state: `claimed`, `completed`, `failed`
- created/updated/expires timestamps
- correlation id

Rules:

- Framework JTI redemption happens before handler execution.
- Domain idempotency is declared and enforced in the backend handler or
  operation. Server route proof metadata can carry the key, but it is not the
  source of enforcement.
- Claim is atomic. A second caller with the same key/JTI cannot enter the
  handler while the first is claimed.
- Successful execution marks the record `completed`.
- Failure marks the record `failed` or releases the claim according to the
  replay mode. The behavior must be declared and tested.
- Cleanup is TTL-based and does not remove active claims.
- Destructive operation execution always uses backend redemption and durable
  audit, even when transport confirmation happened outside Convex.

### 6. Webhooks Are HMAC And Idempotent By Default

Current issue class: shared-secret webhooks are replayable and HMAC idempotency
can be poisoned before parse.

0.3.0 target:

Delete `readSharedSecretWebhookBody` from first-reader exports.

Default helper behavior:

- Secret must be non-empty after trim.
- Signature binds raw body, timestamp, and delivery id.
- Timestamp has a default five-minute tolerance.
- Delivery id must be non-empty.
- Raw body is read once as exact bytes.
- Signature canonicalization is documented: timestamp, delivery id, separator,
  raw bytes, algorithm, and optional key id for rotation.
- Body is parsed and validated before any durable idempotency claim.
- Idempotency is completed in the backend/domain mutation, or through a
  claim/complete/fail store that can recover from backend dispatch failure.
- Duplicate delivery ids return conflict.

Target helper:

```ts
const delivery = await verifyHmacWebhookDelivery(event, {
  secret,
  signatureHeader: 'x-signature',
  timestampHeader: 'x-timestamp',
  deliveryIdHeader: 'x-delivery-id',
  parse: webhookSchema.parse,
})
```

No maintained example should use shared-secret verification before trusted
forwarding.

Webhook idempotency must be durable with the business write. A route-side
consume followed by a failed Convex mutation can drop a valid delivery, so it is
not acceptable as the default production pattern.

### 7. Delegation Requires Binding Evidence

Current issue class: `delegateToUser({ allow: true })` teaches unconditional
impersonation.

0.3.0 target:

Delete boolean delegation from the public server API.

Representation requires a backend-verifiable binding:

```ts
const representation = await requireDelegationBinding(event, {
  service: 'linear',
  workspaceId,
  targetUserId,
  purpose: 'create-task',
})

await serverConvexMutation(event, api.tasks.createFromWebhook, args, {
  auth: transportProof.webhook(delivery, {
    service: 'linear',
    actingFor: representation,
    replay: domainIdempotency({ key: delivery.id, target: api.tasks.createFromWebhook }),
  }),
})
```

Valid binding sources:

- service-to-user allowlist
- OAuth/account connection row
- agent registration row
- workspace membership plus explicit service policy
- explicit delegation grant with expiry

Rules:

- No literal `allow: true`.
- No delegation without subject, workspace, purpose, and grant source.
- Docs and starters must show the binding query beside the trusted call.
- Delegation evidence includes `grantId` or `grantSource`, issuer, service id,
  target user id, workspace id, purpose, expires-at, revocation/version field,
  and reason.
- Target backend handlers must be able to revalidate the evidence or verify its
  signed binding. Server route trust alone is insufficient.
- Forged, expired, revoked, wrong-service, wrong-workspace, wrong-user, and
  wrong-purpose delegation tests are required.

### 8. MCP Is Generated From Backend Authority

Current issue class: MCP tool files can self-certify write safety and omit
permissions.

0.3.0 target:

MCP exposes backend-owned operations and safe queries. Tool files cannot mint
authorization or write safety.

```ts
export default defineMcpApp({
  auth: mcpBearerAuth(),
  tools: (tool) => [
    tool.query('search_pages', searchPages),
    tool.operation('publish_page', publishPage),
    tool.operation('delete_page', deletePage),
  ],
})
```

Rules:

- Delete `stampMcpToolSafety` from the public MCP entrypoint.
- Tool-local safety stamps do not satisfy any write gate.
- Direct MCP mutation tools are deleted from first-reader APIs for 0.3.0.
- Advanced raw tools cannot call `serverConvexMutation`, `serverConvexAction`,
  `ctx.mutation`, or `ctx.action` unless they are on an explicitly unsafe
  surface and fail production doctor.
- Custom MCP tools remain supported for reads and orchestration that does not
  perform app writes.
- If an advanced write path survives for real consumers, it consumes
  backend-owned operation descriptors only. It never accepts MCP-local safety or
  permission metadata.
- MCP sessions bind to bearer `keyId`, `userId`, and `workspaceId`.
- Unexpected backend errors are redacted to a generic message plus correlation
  id.
- Invalid bearer throttling is distributed or doctor marks it non-production.

### 9. Auth Session Is Derived From Better Auth

Current issue class: Trellis client auth can drift from Better Auth session
state.

0.3.0 target:

- Better Auth remains the human session source of truth.
- Trellis auth state subscribes to Better Auth session changes through the best
  available Better Auth client signal, storage/BroadcastChannel signal, or
  explicit wrapped mutation methods.
- Raw Better Auth client access cannot mutate session state without triggering
  Trellis refresh/invalidation.
- Sign-out is complete only after upstream Better Auth sign-out succeeds.
- Failed sign-out leaves UI in an honest error/pending state, not a fake
  unauthenticated state.
- Protected navigation consumes session-change invalidation or performs
  authoritative revalidation.
- Session-authoritative refresh bypasses the recent Convex JWT cache.
- Auth proxy either forwards bodies for all supported methods or rejects
  unsupported method/body combinations explicitly.

Decision:

Do not add a second auth store. Keep one Trellis auth engine, but wire it to the
Better Auth source of truth.

### 10. Public Surface Is Exact

0.3.0 public exports should be intentionally small.

Keep first-reader exports for:

- app definition and Nuxt module setup
- typed handler lanes
- permissions
- operations
- safe server call helpers
- HMAC webhook verification
- verifier-produced trust proofs
- MCP app wrapper over backend operations
- testing helpers that fail closed

Remove or move to internal/unsafe:

- raw identity-forwarding primitives
- raw identity-forwarding context setters
- tool-local MCP safety stamping
- raw advanced MCP write helpers
- shared-secret webhook body reader
- boolean delegation helper
- public MCP key validation/touch examples
- raw test caller fallback

Type/public-surface tests should assert unsafe exports are absent, not merely
that safe exports exist.

Packed artifact acceptance:

- `@lupinum/trellis/server` does not export shared-secret webhook helpers or
  boolean delegation.
- `@lupinum/trellis/backend` does not export raw identity-forwarding envelope
  constructors/verifiers or context setters.
- `@lupinum/trellis/mcp` does not export tool-local safety stamping.
- Trellis-branded advanced MCP exports cannot perform app writes in production
  paths.
- Type tests include negative import assertions for removed exports.

## Examples And Starters Policy

Agents will copy examples. Humans will review generated code against examples.
Therefore examples are production templates.

0.3.0 example rules:

- No "demo-only but public" backend mutation.
- No public email-to-user-id resolver.
- No static bearer token comparison in production-copyable MCP examples.
- No direct delete in starters unless modeled as destructive operation.
- No trusted route without concrete verifier code in the snippet.
- No weak mocks replacing Trellis security helpers in route tests.
- No unconditional onboarding overwrite.
- No draft/unpublished share-token reads unless exposed through a separately
  named draft-preview capability.

## Proof-First Implementation Program

Convex is powerful, but the hard parts of this release depend on runtime
behavior that should be proven before broad API work starts. 0.3.0 should not
begin by building the final surface. It should begin by proving the invariants
in small harnesses.

Rules:

- No new abstraction ships until its core Convex/runtime behavior has a focused
  proof.
- Each proof has an attacker-shaped test that fails against the old behavior and
  passes against the proposed behavior.
- If a proof shows Convex makes the desired shape brittle, change the design
  before coding the public API.
- Prefer deleting or blocking old unsafe paths before adding replacement
  ergonomics.
- Do not keep old and new paths side by side as normal options.

Required proof spikes:

| Spike                   | Question to prove                                                                           | Minimum proof                                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Raw DB removal          | Can Trellis internals use raw DB without attaching it to handler-visible `ctx.db`?          | Handler attempts symbol/key/prototype/descriptor recovery and fails; destructive confirmation internals still work                       |
| Public-safe DB facade   | Can public handlers get a useful DB facade without tenant/user leakage?                     | Public handler cannot read private users/emails, service tables, workspace data, raw DB, or cross-tenant data                            |
| Strict evaluator        | Can one evaluator power guards, `can`, `enforce`, projection, handlers, and MCP visibility? | Promise/object/string/number/function guard results deny or throw consistently across every surface                                      |
| Cross-tenant capability | Can narrow cross-tenant reads work without exposing a generic DB facade?                    | Named membership/dashboard capability works; adjacent tenant/user negative tests fail closed                                             |
| Service subject         | Can service work be scoped without becoming ambient admin?                                  | Service subject without allowed operations/tables/replay/audit fails doctor/runtime; scoped service can call only its declared operation |
| Trusted proof           | Can route/MCP callers pass opaque proof without user-authored trust literals?               | App code cannot construct proof directly; purpose/transport/args mismatch fails                                                          |
| Replay store            | Can Convex atomically claim/redeem before handler execution?                                | Captured trusted write and destructive execute request reaches handler once; failed execution has declared retry/fail behavior           |
| Webhook idempotency     | Can valid deliveries survive backend dispatch failure?                                      | Parse/signature succeeds, backend write fails, delivery is retryable or marked failed, not permanently consumed                          |
| Delegation binding      | Can target backend handlers revalidate representation evidence?                             | Forged/expired/revoked/wrong-service/wrong-user/wrong-workspace/wrong-purpose evidence fails                                             |
| MCP operation migration | Can real custom MCP write patterns become operation-backed?                                 | Ginko-style project tool fixture and shadcn-style todo tool fixture migrate without `stampMcpToolSafety`                                 |
| Better Auth sync        | Can Trellis reliably observe session changes?                                               | Other-tab/raw-client sign-in/sign-out/session switch invalidates or refreshes Trellis auth state                                         |
| Packed exports          | Can unsafe exports be absent from built package, not only source?                           | Packed artifact import tests fail for removed unsafe APIs                                                                                |

Experiment artifacts:

- Keep spike tests under focused security/harness files.
- Keep throwaway probes out of the release unless they become regression tests.
- Record any failed proof in this document before implementation proceeds.
- Promote successful proofs into `test:security`.

Implementation entry criteria:

- Phase 0 source-policy checks exist for known unsafe snippets.
- Raw DB removal proof passes.
- Strict evaluator proof passes.
- Replay proof has a viable Convex implementation path.
- Public-safe DB facade is defined and tested.
- Service lane is either fully specified by the proof or explicitly delayed.
- Direct MCP write replacement has at least one consumer-style fixture.

## Design Decisions For Implementation

These decisions define the 0.3.0 implementation direction. Revisit only with
new evidence from implementation or tests.

1. Trusted mutation/action replay

   Decision: every trusted mutation/action must declare replay behavior. Use
   domain idempotency for webhooks and provider events. Use backend JTI
   redemption for framework-managed operation execution. Replay state includes
   claim/complete/fail semantics so failed dispatch does not silently drop valid
   work.

2. MCP transport

   Decision: either sign MCP forwarded calls as `transport: 'mcp'` and test the
   separation, or delete the MCP transport enum value. Do not keep an unused
   security boundary.

3. Cross-tenant access

   Decision: use named capabilities for narrow cross-tenant reads. Reserve
   `unsafe` lanes for broad raw access and framework internals. Do not add a
   generic `admin` lane until a concrete reusable Trellis-owned admin workflow
   proves it is needed.

4. Direct MCP mutation tools

   Decision: remove direct MCP mutation tools from first-reader 0.3.0 APIs. If
   an advanced write path survives for real consumers, it requires
   backend-owned operation descriptors and explicit permissions. MCP-local
   safety metadata is not accepted.

5. Server Convex auth options

   Decision: require explicit auth options in app server route code. Internal
   helpers may default for framework plumbing, but production-copyable code
   should spell the auth mode.

6. Service lane

   Decision: ship `service` only with a full service-subject contract. If the
   implementation cannot make service scope, replay, acting-for, and audit
   explicit, delay the lane.

7. Security contract

   Decision: build the Phase A exact contract first. Do not attempt broad route
   proof/delegation introspection until the smaller contract reliably catches
   real regressions.

## Summary

The 0.3.0 plan is to make Trellis smaller and stricter:

- backend lanes declare capability
- one evaluator decides authorization
- tenant isolation has no hidden raw DB escape
- operations own write metadata
- trusted writes carry verifier proof and replay behavior
- delegation requires binding evidence
- MCP projects backend authority
- Better Auth drives client session truth
- public exports are exact
- examples are production templates
- security tests are attacker-shaped and local

This is a larger refactor than fixing 58 issues one by one, but it should
produce a Trellis that is easier for humans and agents to use correctly.
